# WP REST Updater

Edit remote WordPress content over the REST API. Helper script: `scripts/wp-rest.sh`. Block markup is generated by the project's own block editor, never written by hand.

## When to Use

- Content changes on a site where you only have wp-admin, not SSH or WP-CLI
- Creating a page or post draft from a title and slug
- Changing text or attributes of blocks, or adding whole blocks (core or custom)

Not for: theme or plugin code, media uploads, menus, widgets, deleting content, or changing post status to `publish` without the user asking.

## Setup (once per project)

1. The user creates an Application Password: wp-admin > Users > Profile > Application Passwords. Prefer a user with the Editor role over Administrator.
2. The credentials go in `~/.netrc`, never in the repo or in chat. Remove the spaces from the Application Password (or wrap it in double quotes). An unquoted password with spaces is cut at the first space and returns 401:
   ```
   machine <site-host> login <wp-username> password <application-password-without-spaces>
   ```
3. Set the REST base, including any subpath, in the project's `.claude/settings.local.json` (not committed): `{ "env": { "WP_REST_BASE": "https://<host>[/<subpath>]/wp-json" } }`. A plain `export` does not persist between Bash calls. If the variable is not visible, restart the session.
4. Run `<skill-dir>/scripts/wp-rest.sh whoami`. A 200 with the expected user means auth works. A 401 or 403 means a security plugin, WAF, or host is blocking it, or the password in `~/.netrc` is wrong.

`WP_REST_BASE` must be `https://`. The script refuses anything else because it sends the password with every request. Needs curl 7.76 or later and `jq`.

Backups go to `$WP_REST_BACKUP_DIR` (default `~/.wp-rest-backups`).

## Commands

`<skill-dir>` is this skill's base directory. The working directory is the user's project, so call the script by its absolute path.

```
<skill-dir>/scripts/wp-rest.sh whoami
<skill-dir>/scripts/wp-rest.sh get <pages|posts> <id> <out-file>
<skill-dir>/scripts/wp-rest.sh create <pages|posts> <title> <slug>
<skill-dir>/scripts/wp-rest.sh update <pages|posts> <id> <content-file> <modified>
```

`get` prints `modified`. `update` needs that value, saves the current content to the backup dir, and aborts if the page changed since your `get` or if the content file is missing or empty.

## Workflow

**Create a page**
1. Ask for the title and slug if missing.
2. Run `create`. It always makes a `draft`. Report the id and link.
3. To add content, continue with the edit flow below.

**Edit content**
1. `get` the page into a scratch file. Keep that file as the original and note the `modified` value.
2. Produce the new content (see "Where the markup comes from").
3. Show a diff of original vs new. Do not hide changes outside what the user asked for.
4. Ask the user to confirm. Never call `update` before they say yes.
5. Run `update` with the `modified` value from step 1, then `get` again and compare to the new content. If `update` aborts because the page changed, run `get` again and redo the edit. Report the id, `modified`, and the backup path.

If the user asks to publish, confirm that separately, then POST `{"status":"publish"}` to the same endpoint.

## Where the markup comes from

- **Core blocks with text only in the HTML** (paragraph, heading, list): edit the string directly.
- **Custom blocks, or any block with attributes in the comment JSON**: use the local block editor. Custom static blocks store data twice (comment JSON and saved HTML). Editing one copy leaves the block invalid in the editor. `wp.blocks.parse` and `serialize` update both.
  1. Open the project's local site in the block editor with Playwright. Ask the user for the local URL and login if you do not have them.
  2. Run the snippets in `references/editor-snippets.md` to build new blocks or edit existing ones.
  3. The snippets report invalid blocks. Stop if any appear.
- **Block attributes and type**: read `<blocks-dir>/<name>/block.json`. A `render.php` next to it means a dynamic block, which is saved as a comment only (`<!-- wp:name {...} /-->`).
- **Images**: media upload is not supported. Ask the user for an existing media `id` and `url`.

Local and remote must run the same block code. Confirm the remote has the current build before pushing markup from the local editor.

## Rules

- Drafts by default. Never publish, delete, or change another user's content unless asked.
- One confirmation per write. Approval for one page does not cover another.
- Do not invent content such as figures, names, or dates. Ask for missing data.
- Credentials stay in `~/.netrc`. Never echo or log them.
- Do not test on real pages. Use a scratch draft.

## Known limits

- Re-serializing can change untouched text: a literal non-breaking space (U+00A0) in a rich-text value comes back as `&nbsp;`. It renders the same. If it appears in the diff, tell the user it is not an edit they asked for and let them decide.
- Unverified: whether every page's existing blocks are valid in the editor. The edit snippet stops on invalid blocks.
- Write permission depends on the user's role. The `wp:action-unfiltered-html` link in a page response shows whether the user can save unfiltered HTML. Without it, WordPress may strip markup.
- Edits via REST create revisions only if the site has them enabled. The local backup is the reliable one.
